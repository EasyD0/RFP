# 关于识别误报的进一步工作

>2026-8-26

#### 说明
- 本报告承接 2026-8-17 的汇报《关于5个规则的识别误报》, 总结 8-17 晚至 8-26 的主要进展
- 新增规则 **132S <不能在逻辑表达式中使用赋值>**, 规则数由 5 条变为 6 条
- 47S 的"数组长度检查确保不越界"由占位实现升级为完整的**约束分析**
- 36S 的"所有引用处都没有使用返回值"改用 **libclang AST** 精确实现
- 对 **clangd 工具**做了工程化改造: 长驻会话 / 应答 server->client 请求 / 多进程版本
- 核心原则不变: **识别误报必须没有误报 (无虚警)**, 不确定时保守不判
- 目前程序采用"建议式": 识别为误报的条目不会删除, 而是给出提示

#### 识别程序介绍
识别程序先检查问题所属规则, 然后逐一检查是否符合其中某条*误报标签*。
- *误报标签* 来自于对历史数据的分析
其中一条命中则标记为误报, 否则不做标记。

## 47S-数组越界
> **降低误报的要求**: 有明确防护的代码, 如变量被 for 循环限制、被宏限制, 确认防护值不会越界即可

在 8-17 汇报中, 该规则的"普通变量下标"只检查上一层 (占位); 本次已完整实现**约束提取** `get_constraint`。

###### 约束提取 get_constraint
**核心逻辑:**
1. 从规则名中解析数组名和下标变量
2. 定位包含下标访问的约束语句 (for / while / if), 提取其中对下标变量的比较约束
   - 支持 `&&` 组合 (`i >= 0 && i < 10`)
   - 支持反向书写 (`0 <= i`) 与括号包裹
3. 对 for 循环, 从初始化 `i = C` 与递进方向推导边界:
   - 递增 (`++i` 等) → 下界 `i >= C`
   - 递减 (`--i` 等) → 上界 `i <= C`
4. 常量求值: 整型字面量 (含 hex/octal/binary/后缀) / 简单对象宏 (`#define N 10`) / 枚举常量 / `const int`
5. 无符号下标类型天然满足下界 `i >= 0`

**如何确保不虚警:**
- 只分析有效区域: for / while 循环体、if 的 then 分支; 条件、else 分支、循环后访问不适用
- 保守检查约束区域内下标变量是否被修改 (赋值 / 复合赋值 / 自增自减), 被修改则不判
- 只做单层检查, 不追踪跨语句数据流; switch / do-while 暂不支持 → 保守不判
- 有符号整型缺少下界 (如只有 `i < 10` 而没有 `i >= 0`) → 不判
- 用 AST 定位下标表达式, 而非正则

**必要条件:** 编译参数 和 libclang 是可信的

**验证:** 33 个测试用例全部通过 (`test/test_47s.py`), 覆盖无约束 / 界内 / 上界过大 / else 分支 / 循环体内修改下标 / 递减 / 无符号 / 宏上界 / 缺下界 / switch 不支持等场景

## 36S-函数没有返回语句
> **降低误报的要求**: 所有引用处都不使用返回值

8-17 晚上开始迭代实现, 现改用 libclang AST 精确判断返回值是否被使用。

###### 所有引用处都没有使用返回值
**核心逻辑:**
1. 通过 clangd 定位函数的所有引用
2. 对每个引用处, 用 libclang AST 找到最内层 CallExpr, 检查其直接父节点:
   - `CompoundStmt` → 独立语句, 返回值未使用
   - `CStyleCastExpr(→void)` → 显式丢弃, 未使用
   - 无大括号的控制流语句体 (`for (;;) foo(1);` 等) → 未使用
   - 其他 (作为参数 / 运算 / return) → 返回值被使用
3. 若所有引用处都不使用返回值, 则视为误报

**如何确保不虚警:**
- 可正确处理跨行调用 `g(\n f(x)\n)` 与注释行
- 无大括号的 for / while / do / if / switch / case 体中的独立调用视为未使用

**必要条件:** 编译参数 和 libclang 是可信的; clangd 定位引用可靠

> 另: 记录了**列号单位问题** — clangd 用 UTF-16 列, libclang 用 UTF-8 字节列, Python 用 Unicode 码点列; 同一行出现非 ASCII 字符时三者错位。当前扫描目标多为 ASCII 行, 已暂缓解决 (`列号单位问题.md`)

## 132S-不能在逻辑表达式中使用赋值 (新增规则)
> **降低误报的要求**: 逻辑表达式中的赋值结果以"取值"方式被消费 (比较 / 算术等), 而非直接作为布尔值, 则视为误报

典型形式:

```c
(ret = f(x)) == 0        // 赋值结果被 == 比较
(ret = f(x)) + 1 > 1     // 赋值结果先做算术, 再被 > 比较
```

###### 赋值结果被取值消费
**核心逻辑:**
1. 定位逻辑表达式 (if / while / for / do 的条件, 或独立比较表达式)
2. 收集其中所有赋值节点 (简单 `=` 与复合赋值 `+=` 等)
3. 对每个赋值, 沿父链向上 (跳过括号包装), 判断其结果的消费方式:
   - 遇到比较运算符 (`== != < > <= >=`) → "取值"使用
   - 遇到其它取值运算符 (`=` `+` `-` 函数实参 数组下标 ...) → 继续向上, 看是否最终流入比较
   - 先遇到逻辑布尔边界 (`&&` `||` `!` 三元条件 表达式顶层) → "布尔"使用
4. 仅当表达式内**所有**赋值都以"取值"方式被消费, 才视为误报

###### 对 (ret = f(x)) + 1 > 1 的考虑
赋值结果不直接作为比较的操作数, 而是先经过算术 `+` 再参与比较 `>`。若只看
"赋值是否直接作为比较的操作数"会漏掉这一类, 因此沿父链向上穿过取值运算符。
注意若向上先遇到逻辑布尔边界则判定为布尔使用 (不判误报), 例如:

```c
((ret = f()) && y) == 1   // 赋值直接是 && 的操作数 → 布尔使用, 不判
ret = f() == 0            // 顶层赋值, 比较在右侧 → 不判
```

**如何确保不虚警:**
- 只分析控制语句的条件部分, 不计入同一行循环体 / 分支里的赋值
- 所有赋值都必须"取值使用"才判; 混合情形 `(ret=f())==0 && (y=g())` 不判
- 解析失败 / 游标为空 → 不判

**必要条件:** 编译参数 和 libclang 是可信的

**验证:** 16 个测试用例全部通过 (`test/test_132s.py`), 覆盖独立表达式 / if / while / for / 复合赋值 / 算术+比较 / 逻辑非 / 三元 / 混合 / 比较在右侧等场景

## clangd 工具工程化 (支撑 36S)
> clangd 通过 LSP 提供服务, 依赖 compile_commands.json

###### 长驻会话与缓存
**核心逻辑:** 将 "进程 + 是否已确认索引完成" 绑定为 `ClangdSession`, 按 `(project_dir, compile_dir, clangd_exe)` 缓存; 索引等待只在该会话第一次查询时发生一次, 后续查询直接跳过等待。

###### 应答 server->client 请求
**核心逻辑:** clangd 会主动发送 `window/workDoneProgress/create` 等请求; 若不按 LSP 规范应答, clangd 会一直等待该应答、不再处理后续客户端请求 (死锁)。reader 线程区分"对我们请求的响应"与"clangd 主动请求", 对后者立即应答。

###### 修正索引等待超时判断
- 修复 `first_message_timeout` 被滞后一个 `idle_timeout` 的问题 (30s 变 60s)
- 修复非 `$/progress` 通知不断时永不进入超时分支、只能等 1 小时的问题
- 持续消费 clangd stderr, 防止管道写满阻塞 stdout

###### compile_commands.json 生成与多进程
**核心逻辑:**
- `generate_command_json`: 从宏 / 头文件信息生成 `compile_commands.json` (arguments 数组形式)
- 多进程版本: worker 通过 initializer 复用反序列化的 CodeContext, 不重复初始化、无文件竞态; 退出后清理孤儿 clangd 进程
