# 关于5个规则的识别误报

>2026-8-17

#### 说明
- 对 testbed 报告的代码问题, 采用其他工具审查, 识别其中的误报
- *虚警*定义: 在本工作中, *虚警* 特指 testbed 报告的问题是真命题, 但本程序识别为误报
- **严格来说**, 识别误报的工作**必须没有虚警**, 要做到如上保证, 必须形式上对算法做证明. 然而一些问题可能是不可判定的, 意味着不存在通用算法可解决. 此外, 即使问题是可计算的, 大部分仍然难以给出可形式上证明的算法。
- 此项程序本身也依赖 运行它的操作系统/编程语言软件/其他辅助软件/外界输入参数，只有这些对象都是可信的，且算法形式上可证明，才能说最终结果是可信的。
- 目前程序采用“建议式”：识别为误报的条目不会删除，而是给出提示。
- 在介绍子算法时, 会提及算法结果可信的*必要条件*
#### 识别程序介绍:
 识别程序先检查问题所属规则, 然后逐一检查是否符合其中某条*误报标签*. 
 - *误报标签*来自于对历史数据的分析
 其中一条命中则标记为误报的。否则不做标记。

## 69D-变量未赋值就使用
> **降低误报的要求**: 若在使用值之前已经存在明显的赋值, 则为误报

###### 已在声明处显式初始化
**核心逻辑:** 在声明/定义处已经显式初始化, 视为误报
**如何确保不虚警:** C 语言的初始化语句形式固定, 形式类型有限, 通过遍历所有初始化风格, 模式匹配判断是否为初始化, 可确保该子算法的正确性

###### 全局变量自动零初始化
**核心逻辑:** 利用libclang 检查, 若发现在全局作用域声明/定义, 则视为误报
**必要条件:** 编译参数 和 libclang 是可信的 

###### 静态变量自动零初始化
**核心逻辑:** 若判断为静态变量, 则视为误报
- 检查变量声明处是否存在 `static` 关键字
- 若对于通过宏, 比如 `STATIC` 来指定为静态的, 通过 libclang 工具检查游标的 存储期类型是否为 `StorageClass.STATIC`

**如何确保不虚警:** C 语言中, 前后包含空白字符的"static" 不可能作为除关键字外的其他含义

###### 中途发现初始化语句 (暂未完全实现)
理想中, 我们希望能 扫描所有从变量声明到变量引用的所有可能路径, 检查每条路径 是否存在明显的赋值行为, 从而进行判断
要发现所有可能路径, 需要有算法判定 *某条路径是否可达*, 而该问题可能归约到 *图灵停机问题*, 即可能是不可判定的

**降级方案的逻辑:** 如果没有 `goto` 语句, 可以只检查同一代码结构层级的语句, 举例如下:

```cpp
vodi g(int);

void f(int a){
	int x;
	
	if (a>=0){
		x = 1;	//不是同一层级不考虑
	}else{
		x = 2;  //不是同一层级不考虑
	}
	
	g(x);       // 检查这里是否违规?
}
```

在该算法下, 不会将其标记为误报。目前看来该实现至少不会*虚警*
## 57S-无作用的语句
> **降低误报的要求：** 打印日志语句，汇编语言，置空函数操作
###### 未用的参数
**核心逻辑:** 检查语句是否为 `UNUSED_PARAMETER(...)` 宏调用, 若是则视为误报
现有历史数据里, 存在很多形式为 `UNUSED_PARAMETER` 的违规情况. 从语义上看, 已经说明了它是 *未用参数*, 则无需再报告

###### 日志打印
**核心逻辑:** 提取语句首个 token 处的函数调用名, 若含 `log` 或 `print` 子串则视为误报
**必要条件:** 57S-无作用的语句 违规条目下含含 `log` 或 `print` 的调用里, 没有使用类型 "var1 == var2"  等的表达式.

###### 置为 void
**核心逻辑:** 检查语句是否为 `(void) expr` 形式, 若是则视为误报
**必要条件:** 代码中没有除正则表达式 `\( *void *\)` 的值之外的, 属于 "置为 void" 的语言的字符串.

###### 声明语句
**核心逻辑:** 通过 libclang 获取"无作用语句"的游标, 检查游标类型是否为声明, 若 `cursor.kind == VAR_DECL` 则视为误报
**必要条件:** 编译参数 和 libclang 是可信的 


###### 调用函数
**核心逻辑:** 通过语句的开头的 token 对应的游标, 判断该语句是否为函数调用或函数指针调用:
- `DECL_REF_EXPR` 且定义是 `FUNCTION_DECL` → 函数调用
- `DECL_REF_EXPR` 且原始类型含 `(*)` → 函数指针调用
- `PAREN_EXPR` 且原始类型含 `(*)` → 括号包裹的函数指针调用

**必要条件:** 编译参数 和 libclang 是可信的 
## 1X-在整个系统中声明的类型不一致
###### 代码行没有两处
**核心逻辑:** 若问题代码行不含两处声明, 视为误报

###### 两个声明类型和链接, 存储属性均一致
**核心逻辑:** 基于 libclang 工具, 存储类型/链接属性/类型均可由 游标 精确获取. 获取两处声明的 cursor, 依次比较:
1. 存储类别 (storage_class): 若一方为 `STATIC` 或 `REGISTER` 而另一方不同 → 非误报
2. 链接属性 (linkage): 若一方为 `INTERNAL` 而另一方不同 → 非误报
3. 类型 (type. get_canonical ()): 若底层类型不同 → 非误报

若三者均一致, 则视为误报
## 47-数组越界
> **降低误报的要求：** 有明确防护的代码，如变量被for循环限制、被宏限制，确认防护值不会越界即可

```ad-note
title: 数组越界的不可判定性
求解任意 C 程序是否发生数组越界, *可能*是一个不可判定问题. 见[[#数组越界的不可判定性]]
```

###### 数组长度检查确保不越界
**核心逻辑:**
1. 从规则名中解析数组名和下标
2. 获取数组游标, 获取`数组长度`
3. 获取下标游标, 判断下标类型:
   - 字面量下标: 若 `字面值 >= 数组长度` 则视为误报
   - 枚举常量下标: 若 `枚举值 >= 数组长度` 则视为误报
   - 普通变量下标: 只检查上一层

## 36S-函数没有返回语句
###### 所有引用处都没有使用返回值 (暂未完整实现)
**核心逻辑:**
1. 通过 clangd 定位函数的所有引用
2. 逐个检查引用处代码:
   - 若引用处含赋值运算 `=` → 存在赋值, 非误报
   - 若引用处以 `func_name(` 或 `(void) func_name(` 开头 → 不使用返回值, 跳过
   - 否则 → 使用了返回值, 非误报
3. 若所有引用处都不使用返回值, 则视为误报

```ad-note
title: clangd介绍

- clangd 是为 c/c++提供的语法服务的程序, 它遵从 LSP (标准语法服务协议) 从而可被现代 IDE 使用, 用于代码跳转, 静态检查等.
- 通过LSP即可和clangd通信, 获取它对工程解析的数据, 比如获得函数引用位置
- 它依赖于 `compiler_commands.json` 文件
	- 该文件指定编译命令, 被编译文件等
	- 该文件一般由构建工具生成, 比如 Cmake 等
```

***例子--查找函数 `f` 的所有引用位置:***

```cpp
#include "a.h"  
typedef int int1;  
#define _STATIC static  
int main(){  
    f();  
    _STATIC int1 i;  
    f();  
}
```
