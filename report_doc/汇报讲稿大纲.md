> **静态分析器会报出海量"问题"，其中相当一部分是误报。本项目自动、且"可证明地"识别这些误报，把人从纯人工复核里解放出来——核心承诺是：认错的一定是错误，宁可漏认，绝不误杀真缺陷。**

## 第 2 页 · 从哪里来：问题背景

**上级要解决的一个工程/测试痛点：**
- 静态分析工具（如 Testbed 一类规则检查器）会在源码上报告大量"问题"，每个问题包含文件名、函数、代码行、规则名等信息。
- **大量报告是误报**——代码其实没违反规则，分析器却报了。
- 现状：需要人工一条条点开、看代码、判断真伪。**成本高、枯燥、且判断标准因人而异。**

**用一张漏斗图：** 上报问题总数 → 误报 → 真实缺陷。
- （示意数字，用来制造"原来这么低效"的感受）9 成是误报、1 成是真问题。

## 第 3 页 · 为什么这件事"难"（关键转承）

- 别人为什么不做、或者做了也踩坑？因为**"某个问题是不是误报"本质上是一个不可判定的语义判断**。
- 具体例子：判断"数组会不会越界"——**对任意 C 程序不存在通用的精确算法**（可归约到停机问题 / Rice 定理，证明放附录）。
- 这解释了两件事：
  1. 为什么业界分析器本身会误报（它必须在漏报和误报之间取舍）；
  2. 为什么"想自动判误报"最容易走进**启发式猜法**的坑——按函数名取名、看着像就判，那是拿真缺陷去赌。

**这一页的作用：立起"我们不是拍脑袋猜"的差别。**

## 第 4 页 · 我们的解法：无虚警保证（全篇灵魂）

我们的原则，用一句话公式讲：

> **只要被识别为误报，就必须真的（高概率确定）是误报；不确定的时候，宁可保守不判，把问题留住，也不冒险漏掉真缺陷。**
> —— 宁可漏判，绝不误杀。

对应让"判了必对"的三类可验证依据：
| 依据 | 例子 |
| --- | --- |
| 形式固定的写法（正则精确匹配） | 宏调用、`(void)` 表达式、`&var` |
| 可判定的语法/语义属性 | 全局作用域、静态存储期、编译期常量下标 |
| 可靠的 AST 语义信息（libclang） | 存储类别、链接属性、canonical 类型、数组长度 |

**反问领导一句（口头）**："您更愿意少识别几个误报，还是愿意它偶尔漏掉一个真实的 bug？"——答案导向我们的**保守策略**。

## 第 5 页 · 技术怎么实现：三板斧

一张对比表，讲清"什么场景用哪把锤子"：

| 工具 | 角色 | 适用场景 |
| --- | --- | --- |
| 正则 / 文本匹配 | 识别写法固定的模式 | 形式固定，正确性可保证，成本最低 |
| **libclang**（AST） | 语法 + 语义分析 | 需要存储类别、类型、数组长度等可靠信息 |
| **clangd**（LSP） | 跨翻译单元的符号引用 | 需要查"所有引用处"（如返回值是否被使用） |

- 强调：clangd 是亮点——常用方案做不到"查全部编译单元的引用"，我们**用长驻 LSP 会话 + compile_commands.json 实现跨文件追溯**。

## 第 7 页 · 工程架构：怎么把它跑起来

- 一张分层图：**报告入口(data_structure) → 编译上下文(context + Preprocessor) → 调度(runner) → 各规则(rules)**。
- 三个工程上的加分点：
  1. **多进程并行**：worker 复用反序列化后的编译上下文，避免重复初始化；退出时清理孤儿 clangd 进程。
  2. **compile_commands.json**：给 clangd/libclang 统一喂编译参数，保证解析正确。
  3. **模块化注册机制**：新规则"导入即注册"，扩展成本低（对应后面的可扩展性收益）。

## 附录 A · 为什么"数组越界"不可判定（给有技术背景的人/答辩备查）

- 把"运行中是否发生越界"归约到停机问题（Rice 定理）。
- 结论：不存在对**任意**程序精确判定越界的通用算法 → 所以：
  - 分析器自己在"漏报/误报"间取舍（这就是误报的来源）；
  - 我们也只能做**保守近似**，于是"无虚警保证"不只是工程选择，而是理论约束下的必然策略。
